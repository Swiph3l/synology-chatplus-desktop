# WhatsApp provider audit — 2026-10-22

## Before this milestone

The closed Rust and TypeScript registries accepted Synology ChatPlus, Synology
Chat, Slack, Discord and Mattermost. There was no WhatsApp provider ID, URL
policy, icon mapping, bootstrap registration or dedicated unread adapter.
Configuring WhatsApp through another provider would therefore have inherited
incorrect origin and DOM assumptions and is not a supported migration path.

The existing multi-instance architecture already isolated profiles by stable
service ID (`services/<serviceId>`), independently of display name/provider/order.
Only the legacy `chatplus` instance retains the historical default profile.
The normal provider WebView receives no local command capability. Origin-checked
observations travel through the native unread/notification bridge, and browser
notifications are intercepted by the common native notification coordinator.
Notification activation chooses the originating service ID; notification lifecycle
and provider unread lifecycle are separate.

## Implemented boundaries

`whatsapp` is Experimental, with the fixed official entry URL. Top-level navigation
accepts only HTTPS `web.whatsapp.com:443`, excluding credentials, sibling domains,
lookalikes and nonstandard ports. WebView2's normal user agent is retained. Each
configured instance uses its own stable service-ID storage profile; no credentials
are managed by ChatPlus. Native provider theme support is false, so ChatPlus's
Synology-specific dark stylesheet is not injected into WhatsApp.

Unread evidence is deliberately one-sided until an authenticated UI audit is
available. The dedicated adapter recognizes positive numeric unread badges and
explicit unread accessibility labels on dedicated badge elements within visible
rows under `#pane-side`.
Tests cover the seven current application locales. Generic numbers, contact
titles, document title prefixes and message content are not treated as evidence.
Positive badges report boolean unread; numeric visible-row counts are not presented
as provider-wide totals. Absence of evidence is unknown, including empty,
filtered, archived, collapsed, loading or virtualized lists. Even complete ARIA row
metadata cannot prove archives and other hidden surfaces are read.

No safe current-chat/message identifier is verified. The adapter therefore emits
no conversation IDs, active conversation, read acknowledgement or notification
visibility match. Selecting a chat, focusing the service or clicking a toast cannot
clear local unread through this adapter. Current/global read capabilities are
explicitly unsupported; menu actions are hidden. This avoids falsely claiming
remote/server read changes. A future adapter update must verify real UI semantics
without contact/phone scraping, private APIs or bulk interactions.

WhatsApp browser `Notification` requests are handled by the existing central native
coordinator, retaining each service's saved preference, native permission result,
deduplication, preview setting and stable-ID activation route. DOM badge updates
do not synthesize message payloads or additional toasts. Toast clicks restore the
correct instance and delegates to a retained provider-owned notification click
callback when available. ChatPlus constructs no chat URL or guessed identifier;
this callback's actual routing behavior still needs authenticated QA. Native notification dismissal has no unread
meaning.

## Automated evidence and manual QA

Focused tests cover registry/settings/icon/locale integration, exact URL/origin
policy, independent profile persistence across serialization/reordering, bootstrap
source selection, positive boolean/count evidence, unknown/partial DOM, hidden
badges, replaced roots/observer cleanup, unsupported current-chat acknowledgement,
and renderer isolation. Common native coordinator tests cover source pairing,
deduplication and stable service-ID notification activation. Counts in unread-row
fixtures intentionally remain `null` at the service level.

Authenticated QA is pending: QR login, phone-number pairing, linked-device
persistence after reload/restart, logout, real unread markup, focused/unfocused/
minimized/tray-hidden notifications, duplicate suppression and toast activation.
No claim of successful linked-device login, message receipt, remote mark-read or
visual Windows QA is made. WhatsApp must remain Experimental until these checks
are completed with an authorized account. Read capabilities should remain
disabled until their UI behavior is independently verified.

### Follow-up user evidence and notification permission

The user subsequently reported successful QR pairing; their supplied screenshot
showed an authenticated WhatsApp interface and WhatsApp's notification-permission
guidance. This is user-provided evidence, not an independently inspected account
or completed persistence/notification QA. No account, message, contact or pairing
secret was accessed to investigate it.

The “click the lock icon” guidance assumes a full browser address bar, which
ChatPlus's provider WebView does not expose. Native permission handling previously
could persist a browser notification denial when desktop notifications or the
service mute preference were off. Those delivery preferences must not become
persistent browser denials. The new explicit service context-menu action
`Allow provider notifications` grants only the clicked instance's current
validated origin/profile. Reload the service if WhatsApp retains old permission UI;
the saved ChatPlus desktop notification preference and Windows permission still
control native toast delivery. Enabling browser permission does not mark messages
read or change the user's mute preference.

The user also supplied an iPhone pre-link confirmation showing “Microsoft Edge.”
The follow-up [browser identity investigation](WHATSAPP_BRANDING_2026-10-22.md)
traced public first-party code and tested its bundled parser offline. Keeping the
normal Edge identity and appending `ChatPlus/0.5.0-beta.6` still classifies as Edge;
there is no demonstrated supported arbitrary application-name setting. The phone
label has **not** been fixed. The runtime identity remains unchanged, with no
private protocol or device-property manipulation.

### Follow-up evidence boundary audit — 2026-10-23

The implementation was re-audited at commit
`6618985514bfbba2f4c32af9ebb1a032fe0c4219` before changing behavior. Registry,
origin restrictions, per-instance profile paths, normal runtime identity and
unsupported read capabilities were already present. No authenticated provider DOM
or account was inspected during this audit.

One fixture-reproduced ambiguity remained: scanning every row descendant's
`aria-label` could interpret a contact or preview named exactly “2 unread messages”
as unread evidence. The adapter now queries only its existing dedicated
`icon-unread-count` / `unread-count` test identifiers or `unread-count` icon
metadata. It reads no arbitrary contact, preview, action or image label. Tests
retain all seven unread-label languages on semantic badge fixtures and verify
that matching non-badge labels stay unknown; tripwire getters also reject any
attempt to read those labels or their text. No new unverified selector was added.
These dedicated selectors remain conservative fixture coverage, not a claim of
current authenticated WhatsApp markup compatibility. If the real UI uses another
shape, the result remains unknown until a privacy-safe inspection verifies it.

Current/all read capabilities remain unsupported and omitted from the service
menu. Toast activation must not acknowledge unread; only provider/view evidence
or an explicitly supported read action can do so. Linked-device persistence,
focused/background/minimized/tray-hidden delivery and real callback routing still
require Windows acceptance with an authorized account. WhatsApp remains
Experimental.
